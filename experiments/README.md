# Experiment registry

Ids are `<SERIES>-<N>` (`A-1`). A series letter is one **research question**,
stated in `experiments/<SERIES>/PREMISE.md`. Every experiment that serves that
question takes the next number, whether it is a variant of an earlier run, a
control, a different construction, or a different measurement: `A-1`, `A-2`,
`A-3` may look nothing alike. A new letter opens only when the question itself
is abandoned or replaced: the premise was rejected, or the work takes an
entirely different perspective. Editing `PREMISE.md` to say something new is
the signal that a new letter is due. `N = 0` is the series' smoke run.
Layout: `experiments/<SERIES>/<SERIES>-<N>-short-name/`. Tracked inside:

```text
experiment.toml       the manifest (machine-readable; schema below)
RESULT.md             one bounded interpretation of this experiment, written after a run
receipts/<run-id>/    receipt.json, run.log, tracked artifacts under the size cap,
                      and REMOTE.md naming the larger files left on the server
```

Runs themselves live under `outputs/<id>/<run-id>/` and never enter git.

`experiments/LOG.md` is generated by `make log`: one table per series (id,
status, tier, verdict, summary, relations) and a Mermaid graph of the declared
relations, coloured by verdict. GitHub renders it; nothing to install.

## Manifest schema (`experiment.toml`)

| Field | Required | Meaning |
|---|---|---|
| `id` | always | `<SERIES>-<N>`; the directory name starts with it |
| `title` | always | |
| `status` | always | `draft` → `registered` → `running` → `complete` \| `stopped` \| `failed` |
| `evidence` | always | `smoke` \| `exploratory` \| `claim`, chosen by intended use, not cost |
| `question` | always | affirmative sentence naming the phenomenon and estimand |
| `hypothesis` | non-smoke | what is expected and why; not a promised outcome |
| `task` | always | task module under `src/myproject/tasks/` |
| `entrypoint` | non-draft | `scripts/train.py` |
| `config` | always | base config path, normally `configs/base.toml` |
| `[overrides]` | | deltas on the base config; the only allowed place for them |
| `seeds` | always | enumerated literally; the inferential unit |
| `comparison_axes` | non-smoke | what is compared against what |
| `decision_rule` | claim | prospective rule keyed to a threshold |
| `[[outcome_branches]]` | claim | affirmative observed states the rule selects among |
| `[[inputs]]` | non-smoke | every dataset / checkpoint / parent artifact: `name`, `kind`, `identity` the input already carries (HF revision, sha256, commit, run id) |
| `[environment]` | non-smoke | `python`, `lock` (the committed `uv.lock`), `image` (pod image tag), `determinism` (what is and is not deterministic, with tolerances) |
| `[storage]` | | `hf_repo` for models/datasets (Hugging Face), `max_tracked_mb` cap for fetched artifacts |
| `[compute]` | | `gpus`, `gpu_type` (required non-smoke; numerics depend on it), `hours`; used to propose a reservation |
| `[[expected_artifacts]]` | always | `path` relative to the run dir, `track` (fetch into `receipts/`) |
| `claim_ledger_rows` | | ledger row ids this experiment bears on |
| `reviewed_by` | claim | one cross-family review before launch |
| `verdict` | after a run | `pending` \| `success` \| `failure` \| `inconclusive`; needs a terminal `status` |
| `summary` | with a verdict | one affirmative line; this is the row in `experiments/LOG.md` |
| `[[relations]]` | | `to = "A-1"`, `kind = extends \| controls \| contradicts \| reproduces \| motivates`; edges of the experiment graph |

The validator (`src/myproject/registry.py`) enforces every "required" cell
above and raises. `make validate EXP=...` runs it.

## Execution contract

- `scripts/train.py --exp A-1` accepts only `status = "registered"`.
- Each run gets a fresh `outputs/<id>/<run-id>/` created with `exist_ok=False`.
- `receipt.json` is written before the task starts and rewritten in `finally`, so a failed run still leaves a receipt.
- `--reproduce <run-id>` re-runs a `complete` manifest by copying it unchanged into the new run directory. The manifest's status is never edited for a reproduction.
- The manifest transitions `registered` → `running` → `complete|failed` are recorded in the receipt, not by editing the manifest during the run. The owner updates `status` in the manifest after reading the receipt.

## Where results live

- **Models and datasets**: the Hugging Face Hub, repo named in `[storage].hf_repo`.
  `make hf-push EXP=... RUN=...` uploads `outputs/<id>/<run>/` (or chosen paths)
  under `<id>/<run>/` and stamps the receipt with repo and revision.
- **Small results** (receipt, metrics, small plots/tables): fetched into
  `receipts/<run-id>/` and committed. A tracked artifact above
  `[storage].max_tracked_mb` is not fetched.
- **Large results**: stay on the server under `REMOTE_OUTPUT_ROOT/<id>/<run>/`.
  `make fetch-receipt` writes `receipts/<run-id>/REMOTE.md` listing each file
  left behind with its size and full server path. Summaries (`reports/`) cite
  that entry instead of embedding the file.

## Reproducibility contract

Before a non-smoke run, the manifest fixes: the data (`[[inputs]]` with
identities), the GPU class (`compute.gpu_type`), and the training environment
(`[environment]`: Python, the committed lock, the pod image, and a determinism
statement). The validator refuses a manifest missing any of them. The receipt
then records what actually ran (`hardware`: GPU names, driver, torch, CUDA;
`git_commit`; `python`). A mismatch between manifest and receipt is a finding,
not something to edit away.

## Receipt fields

`exp_id`, `run_id`, `status` (`running|complete|failed`), `started_at`,
`ended_at`, `git_commit`, `git_dirty`, `host`, `python`, `hardware` (GPU names,
driver, torch, CUDA), `env` (remote/output roots), `manifest` (a copy),
`resolved_config`, `result` (the task's return dict), `error`.

## Evidence tiers

| Tier | May support |
|---|---|
| `smoke` | code, shape, runtime, artifact boundary. Implementation support only. |
| `exploratory` | a bounded question; may select the next experiment; labelled exploratory forever |
| `claim` | a registered claim; needs a prospective `decision_rule` and one cross-family review before launch |
